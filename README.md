# Wazuh SIEM Lab

## Overview

This project documents the deployment and configuration of a Wazuh-based security monitoring lab. The environment will be used to collect endpoint telemetry, create and test detections, investigate security events, and simulate activity that may be encountered by a SOC analyst.

The Wazuh server was deployed on an Ubuntu Server 24.04 LTS virtual machine.

- Enabled OpenSSH during installation for remote administration
- Installed Wazuh

The Ubuntu VM will act as the central Wazuh server for the lab, receiving and analysing telemetry from endpoints added later in the project.

## Enabling Wazuh Archives

By default, Wazuh primarily focuses on events that match rules and generate alerts. For this lab, **archives were enabled so that Wazuh retains all received telemetry**, including events that do not trigger an alert.

This is useful in a SOC lab because an event may still be valuable during an investigation even if it did not initially match a detection rule. Retaining the raw telemetry also allows historical events to be searched, suspicious behaviour to be investigated, and new detection rules to be developed from previously collected data.

### Enable Archives on the Wazuh Manager

The Wazuh manager configuration file was modified:

```text
/var/ossec/etc/ossec.conf
```

The following settings were changed to `yes`:

```xml
<logall>yes</logall>
<logall_json>yes</logall_json>
```

- `logall` enables Wazuh to archive all received events.
- `logall_json` stores the archived events in JSON format, making them suitable for indexing and searching.

After making changes to `ossec.conf`, the Wazuh manager must be restarted for the configuration to take effect:

```bash
systemctl restart wazuh-manager.service
```

### Configure Filebeat

Although Wazuh is now archiving the events, Filebeat also needs to be configured to send the archived data to the Wazuh indexer so that it can be searched through the dashboard.

The Filebeat configuration file is located at:

```text
/etc/filebeat/filebeat.yml
```

I opened the configuration:

```bash
nano /etc/filebeat/filebeat.yml
```

Archive indexing was enabled by changing:

```yaml
archives:
  enabled: true
```

Filebeat was then restarted to apply the change:

```bash
systemctl restart filebeat
```

### Create the Archives Index Pattern

**Dashboard Management → Index Patterns**

There was no existing index pattern for the Wazuh archives, so I created:

## Windows Sysmon Configuration

To improve the telemetry available from the Windows endpoint, I installed **Sysmon (System Monitor)**.

Sysmon is part of Microsoft's Sysinternals suite and runs as a Windows system service. It records detailed information about activity occurring on an endpoint that is particularly useful for security monitoring and incident investigation.

This can include events such as:

- Process creation
- Network connections
- File creation
- Registry activity
- Process access
- Driver and image loading
- DNS queries

This provides much greater visibility into endpoint behaviour than relying only on standard Windows event logs.

### Olaf Hartong Sysmon Configuration

Rather than using Sysmon with a basic configuration, I used the community-maintained **Olaf Hartong Sysmon configuration**.

The configuration defines which activity Sysmon should record and which events should be excluded. It is designed with security monitoring and threat detection in mind, providing useful telemetry while filtering some of the unnecessary noise that would otherwise be generated.

This makes it particularly suitable for a SOC/SIEM environment where Sysmon telemetry will later be used for detection and investigation.

Sysmon was installed with the configuration using:

```powershell
.\Sysmon.exe -i .\sysmonconfig.xml
```

## Forwarding Windows Sysmon Events to Wazuh

Installing Sysmon causes Windows to begin generating the additional telemetry, but the Wazuh agent also needs to be instructed to collect the Sysmon event channel.

The Wazuh agent configuration is stored at:

```text
C:\Program Files (x86)\ossec-agent\ossec.conf
```

Because the file requires administrative permissions to modify, I opened **Notepad as Administrator**, selected **All Files**, and opened `ossec.conf`.

The following configuration was added:

```xml
<localfile>
  <location>Microsoft-Windows-Sysmon/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
```

This instructs the Wazuh agent to monitor the Windows Sysmon Operational event channel and forward those events to the Wazuh server.

The Wazuh agent was then restarted to apply the configuration.

### Understanding Subject and Target

An important part of analysing Windows Security events is distinguishing between the **Subject** and the **Target Account**.

The **Subject** generally identifies the security principal responsible for performing the action.

In this event:

```text
Account Name:    MyDFIR
Account Domain:  DESKTOP-J7KDPKR
```

This tells us that the `MyDFIR` account on `DESKTOP-J7KDPKR` performed the account deletion.

The **Target Account** identifies the account that the action was performed against:

```text
Account Name:    student1
Account Domain:  DESKTOP-J7KDPKR
```

Therefore, the event can be interpreted as:

> The `MyDFIR` account on `DESKTOP-J7KDPKR` deleted the local `student1` account on `DESKTOP-J7KDPKR`.

## Security Identifiers (SIDs)

Windows uses a **Security Identifier (SID)** to uniquely identify security principals such as users and groups.

For example, the deleted `student1` account had the SID:

```text
S-1-5-21-2046687144-963757887-2302240994-1002
```

The final value is the **Relative Identifier (RID)**:

```text
1002
```

The preceding portion identifies the authority/domain context, while the RID uniquely identifies the account relative to that SID authority. This is why two local accounts on the same Windows installation will share much of their SID but have different values at the end.

For example:

```text
MyDFIR
S-1-5-21-2046687144-963757887-2302240994-1001
                                              └─ RID 1001

student1
S-1-5-21-2046687144-963757887-2302240994-1002
                                              └─ RID 1002
```

Windows also has **well-known SIDs**. These identify standard accounts and groups whose identifiers remain consistent across Windows installations. Examples include principals such as SYSTEM and built-in groups.

More information on Windows SIDs:

https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-identifiers

### Investigating Event ID 4720

Filtering `data.win.system.eventID` for `4720` returned one result. Looking at `data.win.system.message` showed that the `MyDFIR` account created the new `student1` account:

```text
Subject:
    Account Name:    MyDFIR
    Account Domain:  DESKTOP-J7KDPKR

New Account:
    Account Name:    student1
    Account Domain:  DESKTOP-J7KDPKR

Attributes:
    Primary Group ID: 513
    New UAC Value:    0x15
```

The **Subject** identifies who performed the action, while **New Account** identifies the account that was created. The remaining attributes provide information about how the new account was configured.

Microsoft's documentation for Event 4720:

https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4720

#### Primary Group ID

The event shows:

```text
Primary Group ID: 513
```

According to the Event 4720 documentation, `513` corresponds to **Domain Users**, or **Users for local accounts**.

As `student1` is a local account, this indicates its primary group is the local **Users** group.

#### User Account Control (UAC) Value

The event also contains:

```text
New UAC Value: 0x15
```

Here, UAC refers to **User Account Control flags associated with the account**.

The value is a **bitmask**, meaning `0x15` represents several flags combined together. Microsoft's SAMR documentation lists the individual values:

https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-samr/b10cfda1-f24f-441b-8f43-80cb93e786ec

For this event:

```text
0x10  USER_NORMAL_ACCOUNT
0x04  USER_PASSWORD_NOT_REQUIRED
0x01  USER_ACCOUNT_DISABLED
----
0x15
```

Therefore, `0x15` tells us that the account was created as a normal user account, was initially disabled, and had the **Password Not Required** flag enabled.

This matches exactly what Wazuh shows in the decoded event:

```text
User Account Control:
    Account Disabled
    'Password Not Required' - Enabled
    'Normal Account' - Enabled
```

This demonstrates how the raw hexadecimal value in a Windows event can be decoded to understand the configuration and state of an account when it was created.



### Investigating Event ID 4624

Next, I searched for **Security Event ID `4624`**:

https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4624

> **An account was successfully logged on.**

This returned four events. Looking at the first event under `data.win.system.message` showed information about a successful logon to the Windows machine.

One of the most important fields is:

```text
Logon Information:
    Logon Type: 2
```

According to Microsoft's documentation, **Logon Type 2** represents an **Interactive** logon — a user logging on directly at the keyboard and screen of the computer.

This is important during an investigation because different logon types can help determine **how an account accessed a system**, such as locally, over the network or through Remote Desktop.

### New Logon

The `New Logon` section identifies the account for which the new logon session was created:

```text
New Logon:
    Account Name:    MyDFIR
    Account Domain:  DESKTOP-J7KDPKR
    Logon ID:        0x32A8A99
    Linked Logon ID: 0x32A8A67
```

The account logged in was therefore:

```text
DESKTOP-J7KDPKR\MyDFIR
```

On a domain-joined machine, `Account Domain` may contain the Active Directory domain. Because this is a local account, it instead shows the computer name.

The **Logon ID** is particularly useful during an investigation because it identifies the logon session and can be correlated with other Windows events associated with the same session. The **Linked Logon ID**, when populated, can link this session to a related logon session.

### Additional Information

The event also provides useful process information:

```text
Process Name:
C:\Windows\System32\svchost.exe
```

This identifies the process associated with requesting the logon and can help determine whether the authentication activity is consistent with normal Windows behaviour or potentially suspicious.

The event also contains:

```text
Source Network Address: 127.0.0.1
```

`127.0.0.1` is the IPv4 loopback address, meaning the connection originated from the **local machine itself**, rather than another host on the network.

Event ID `4624` gives us much more than just knowing a login was successful. We can use it to see **who logged in, how they logged in, where the login came from, and link the login to other activity during the same session**.


### Investigating Event ID 4732

Lastly, I searched for **Security Event ID `4732`**:

> **A member was added to a security-enabled local group.**

This returned two events. Looking at one of them showed:

```text
Subject:
    Account Name:    MyDFIR
    Account Domain:  DESKTOP-J7KDPKR

Member:
    Security ID:     S-1-5-21-2046687144-963757887-2302240994-1002
    Account Name:    -

Group:
    Security ID:     S-1-5-32-544
    Group Name:      Administrators
    Group Domain:    Builtin
```

The **Subject** shows that `MyDFIR` performed the action, while the **Group** section shows that a member was added to the local `Administrators` group.

However, the `Member` section does not provide an account name:

```text
Account Name: -
```

Instead, we only have the SID:

```text
S-1-5-21-2046687144-963757887-2302240994-1002
```

This is a good example of why understanding SIDs and RIDs is useful during an investigation. Logs will not always provide a convenient username, so sometimes we need to correlate the SID with other events to work out which account it belongs to.

I copied the SID, placed it in quotes and searched for it in Wazuh:

```text
"S-1-5-21-2046687144-963757887-2302240994-1002"
```

Other events containing this SID identified the account as:

```text
student1
```

We can therefore determine that the event represents:

```text
MyDFIR → added student1 → local Administrators group
```

This also links back to the earlier Event ID `4720`, where `student1` was created with the same SID ending in RID `1002`.

Being able to correlate identifiers like SIDs across different events is useful when a single log does not contain all the information needed to understand what happened.

When the SSH connection was closed, Wazuh recorded:


This event does not directly state `Session 2`, but other information can still be used for correlation. For example, `sshd[2304]` is the same SSH process seen when the session was opened:


This allows activity associated with the same SSH process to be connected during an investigation.

### Account Management Chart

The chart shows **Windows account-management activity over time**, split by Event ID. Each Event ID represents a different action, such as creating or deleting a user, enabling an account, or adding/removing users from local groups.

The X-axis shows **when the events occurred** in 5-minute intervals, while the Y-axis shows **how many events occurred**. Splitting the data by Event ID makes it easier to quickly see what types of account changes were happening and when.

This is useful because it gives an analyst a quick view of **account-related changes and unusual spikes in activity** without having to search through individual logs. Events such as unexpected account creation or changes to privileged group membership can then be investigated further.
